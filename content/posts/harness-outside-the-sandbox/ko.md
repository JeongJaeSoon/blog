에이전트용 샌드박스를 설계하다가 이런 질문을 받았습니다. 혼자 쓸 때는 VM 하나에 하네스까지 넣는 게 제일 간단한데, 에이전트 수천 개를 돌리는 팩토리라면 에이전트마다 VM을 붙이는 순간 CPU가 먼저 바닥나지 않느냐는 것이었습니다.

제 답은 "대규모라면 하네스를 샌드박스 밖으로 빼야 한다"였습니다. 근거로 가장 먼저 꺼낸 건 Anthropic이 Claude Managed Agents를 다시 짜면서 공개한 숫자입니다. 하네스를 컨테이너 밖으로 빼고 컨테이너를 필요할 때만 만들게 바꾼 뒤, 첫 토큰까지 걸리는 시간이 p50 기준 약 60%, p95 기준 90% 이상 줄었다고 합니다. 샌드박스를 기다리지 않아도 되는 세션이 그만큼 많았다는 뜻입니다.

답을 정리하다 보니 글로만 두기 아까워서 해설 영상도 만들었습니다. 내레이션은 로컬 TTS로 넣었는데, 목소리를 자연스럽게 만드는 데 설계 정리보다 시간이 더 들었습니다. 그 과정은 아래에 따로 남겼습니다.

![하네스를 샌드박스 밖으로 빼야 하는 이유를 설명하는 7분 28초 해설 영상](/videos/harness-outside-the-sandbox-ko.mp4)

## CPU 말고도 밖으로 빼야 하는 이유가 세 가지 있다

질문은 CPU에서 시작했지만, 하네스와 샌드박스를 한 컨테이너에 두면 생기는 문제는 그보다 많습니다.

첫째는 신뢰성입니다. 하네스와 루프의 상태가 같은 컨테이너에 있으면 컨테이너가 죽는 순간 세션도 같이 사라집니다. 둘째는 보안입니다. 에이전트가 임의의 코드를 실행하는 곳에 credential이 있으면, 그 코드가 credential에 닿지 못하게 막는 일 자체가 어려워집니다. 샌드박스 밖에서 토큰을 쥔 proxy를 두면 샌드박스 안에서는 처음부터 손이 닿지 않습니다. 셋째는 기동 속도입니다. 샌드박스가 필요 없는 세션이라면 VM이 뜰 때까지 기다리지 않고 바로 추론을 시작할 수 있습니다. 위에서 본 60%가 이 효과입니다.

## 상태를 세션에 두면 쿠버네티스와 같은 모양이 된다

구조는 쿠버네티스 위에서 도는 대규모 애플리케이션에 빗대면 쉽게 정리됩니다.

| 구성 요소 | 쿠버네티스로 치면 | 역할 |
|---|---|---|
| Harness · Loop | Deployment (stateless) | 죽으면 새로 띄운다 |
| Session · Event Log | etcd / DB | 하네스 밖에 남는 append-only 로그 |
| Sandbox | Job / Pod | 필요할 때 띄우고, 쓰고, 버린다 |
| Orchestration | Control Plane | 하네스를 깨우고 샌드박스를 준비한다 |

핵심은 상태를 하네스 안이 아니라 세션에 둔다는 점입니다. 루프가 상태를 들고 있지 않으니 아무 하네스 인스턴스가 세션 로그를 읽고 이어서 돌면 됩니다. 그래서 루프를 공유 인프라 위에서 stateless하게 돌릴 수 있습니다.

## 루프는 대부분의 시간을 LLM 응답을 기다리며 보낸다

처음 질문으로 돌아가면, 루프를 밖으로 빼는 순간 CPU 문제의 모양이 바뀝니다. 루프가 하는 일의 대부분은 LLM 응답을 기다리는 것이라 VM을 차지할 이유가 없습니다. VM이 필요한 건 에이전트가 실제로 코드를 실행하거나 파일을 만지는 동안뿐입니다.

그래서 상주 VM을 나눠 주는 대신 작업 단위로 띄우면 됩니다. 짧은 실행은 AWS Lambda나 Cloud Run functions 같은 FaaS로 충분합니다. Computer-Use나 Browser-Use처럼 길고 무거운 실행은 그때그때 VM을 띄우고, 넘치는 작업은 Queue에 쌓아 순서대로 처리합니다.

최근 나온 도구들이 이 방향을 더 쉽게 만들고 있습니다. Code mode나 가상 bash·파일 시스템이 있으면 읽고 찾고 조금 고치는 작업은 VM 없이 끝납니다. Durable Objects, Vercel Workflows, Temporal 같은 durable 실행 기반은 루프의 상태를 바깥에 두는 일 자체를 맡아 줍니다.

## VM을 유지한 채 CPU만 비우는 방법도 있다

같은 문제를 다르게 푸는 쪽도 있습니다. 두 글을 나란히 읽어 보면 차이가 분명합니다.

[mendral](https://mendral.com/blog/agent-harness-belongs-outside-sandbox)은 하네스를 백엔드에서 돌리고 샌드박스는 명령을 실행할 때만 깨웁니다. LLM을 호출하는 동안에는 샌드박스를 멈춰 두고, 다시 깨우는 데 약 25ms가 든다고 합니다. Managed Agents와 같은 방향입니다.

[Agent Substrate](https://ate.dev)는 반대로 에이전트마다 microVM이나 gVisor 샌드박스를 하나씩 줍니다. 대신 쉬고 있는 에이전트는 일시 정지했다가, 준비된 아무 워커에서나 500ms 안에 메모리와 파일 시스템 상태 그대로 다시 깨웁니다. VM은 그대로 두고 CPU만 비우는 방식입니다.

후자라면 에이전트마다 VM을 붙이면서도 CPU 병목을 꽤 줄일 수 있습니다. 어떤 작업에 어느 쪽이 맞는지는 제가 아직 직접 재 보지 못했습니다. 이 부분은 검증이 필요한 채로 남아 있습니다.

## 두뇌와 손 중에서 아직 비어 있는 곳

하네스를 밖으로 빼고 나면 남는 질문은 "두뇌(Brain)와 손(Hands)을 만드는 도구가 충분히 갖춰졌는가"입니다. 제 판단은 반반입니다.

추론은 여러 LLM을 프록시 하나로 묶어 쓰면 되고, 지식으로서의 스킬은 플러그인 마켓플레이스로 나눠 쓰는 방식이 자리를 잡았습니다. 손 쪽 도구는 MCP Gateway를 두면 사내 시스템으로 가는 창구와, credential을 샌드박스 밖에서 쥐는 proxy 역할을 한곳에서 맡길 수 있습니다.

비어 있는 곳은 기억과 실행입니다. 단기 기억은 컨텍스트 윈도우가 이미 한계라서, Managed Agents의 Dreaming처럼 세션 사이에 기억을 정리하는 장치가 따로 필요합니다. 장기 기억은 벡터 검색만으로는 관계와 맥락이 남지 않아서, LLM Wiki 같은 지식 베이스에 더해 사내 문서를 그래프나 온톨로지로 엮는 작업이 필요합니다. 실행 쪽은 스크립트나 Computer-Use, Browser-Use를 실제로 돌릴 VM이 아직 필요합니다.

## 하네스와 함께 설계해야 하는 세 가지

두뇌와 손만으로는 에이전트가 정해진 방향대로 안정적으로 움직이지 않습니다. 하네스를 설계할 때 같이 넣어야 한다고 본 것이 세 가지 더 있습니다.

- **눈과 귀 (Perception)**: 손이 움직인 결과를 관측해서 다시 두뇌로 돌려보내는 피드백 루프입니다. 실행 뒤에 스스로 결과를 돌아보는 Self-Reflection도 여기에 넣었습니다.
- **자율신경계 (Guardrails)**: 데이터베이스 전체 삭제, 허락 없는 결제, 무한 루프 같은 행동을 막고, 실행 전에 사람의 승인을 받습니다. 손을 움직이기 전에 LLM-as-a-Judge로 한 번 더 보는 Online Eval도 이쪽입니다.
- **제어 엔진 (Orchestration)**: 생각하고 움직이고 확인하는 순환 전체를 관리하고, 실패하면 재시도하거나 다른 길로 돌아갑니다. 이때 필요한 상태도 루프가 아니라 세션에 둡니다.

Observability와 Offline Eval은 실시간 실행에 직접 끼어들지 않아서 여기서는 뺐습니다.

## 영상은 로컬 TTS로 만들었고 목소리를 세 번 바꿨다

화면은 HTML과 CSS로 장면 13개를 만들고, Playwright의 WebKit으로 1/30초마다 한 장씩 캡처해 ffmpeg로 1080p 영상으로 묶었습니다. 처음 일본어판은 macOS의 `say` 명령으로 내레이션을 넣었는데, 기계음이 너무 티가 나서 한국어판은 로컬 모델을 쓰기로 했습니다.

고른 모델은 Qwen3-TTS 1.7B CustomVoice의 MLX 8bit 변환본(약 3.1GB, Apache-2.0)이고, 화자는 한국어 화자인 Sohee입니다. 내레이션은 문장 44개로 나눠 한 문장씩 만들고, 장면마다 이어 붙였습니다.

첫 결과물은 쉼이 문제였습니다. 쉼표마다 0.4~0.7초씩 멈췄고, 길게는 1.7초를 쉬는 문장도 있었습니다. 대본이 일본어를 옮긴 문장투라 쉼표가 많았던 탓도 있어서, 대본을 구어체로 처음부터 다시 쓰고 쉼표를 줄였습니다.

두 번째 시도에서는 모델에 "경쾌하게, 쉼표에서 멈추지 말고"라고 지시하고 문장 안의 쉼을 0.2초 수준으로 깎은 다음 1.06배 빠르게 재생했습니다. 쉼은 사라졌지만, 들어 보니 귀찮아하거나 화난 사람처럼 들렸습니다. 지시와 가속과 쉼 제거가 겹치면서 말투가 몰아붙이는 쪽으로 간 것입니다.

마지막에는 같은 두 문장을 "밝고 다정하게", "차분하고 부드럽게", 그리고 지시 없음으로 만들어 비교했고, 지시 없는 기본 톤이 가장 자연스러웠습니다. 최종 설정은 이렇습니다.

```sh
# 문장 안에서 0.35초를 넘는 쉼만 0.3초로 줄이고, 속도는 건드리지 않는다
ffmpeg -i s3_1.wav -af "silenceremove=start_periods=1:start_threshold=-42dB:stop_periods=-1:stop_duration=0.35:stop_silence=0.3:stop_threshold=-42dB" out.wav
```

문장 사이는 0.45초, 장면이 바뀔 때는 1초 정도를 따로 넣었습니다. 기본 톤은 앞선 설정보다 느긋해서 영상 길이가 7분 28초로 늘었습니다. 하지만 빠르고 퉁명스러운 5분보다는 낫다고 판단했습니다.

이 글의 일본어판과 영어판 영상은 같은 설정에서 화자만 바꿔 다시 만들었습니다. 일본어는 Ono_Anna, 영어는 Serena입니다.

## 남은 질문

하네스 분리형과 VM 유지형 중 어느 쪽이 어떤 작업에 맞는지는 아직 답을 내지 못했습니다. 짧은 도구 호출이 대부분인 에이전트라면 하네스 분리형이, 브라우저를 오래 붙잡고 있는 에이전트라면 VM 유지형이 유리할 것 같지만 아직 추측입니다. 직접 재 보면 이어서 쓰겠습니다.
