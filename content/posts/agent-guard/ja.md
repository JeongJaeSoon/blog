このツールは、問題が面白そうだったから作ったのではありません。目の前で何度も起きたから作りました。

職場では実際的開発にClaude Codeを多用しています。セッションが同じ静かな形で崩れることが、一度ではなく何度もありました。エージェントが通常の作業中に`.env`ファイルを読み、本物のAPIキーがトランスクリプトの中に入ります。キーはLLMへ渡り、セッションログに残り、コピーひとつで本来行くべきでない場所へ行ける状態になりました。警報が鳴ることも、誰かが無謀なことをしたこともありません。エージェントは自分の仕事をしていただけです。その仕事とは、ファイルを読み、コマンドを実行することです。

r/ClaudeCodeの投稿も同じ話をしています。ある開発者は、エージェントが`.env`から複数プロバイダのキーを取り出し、トークンを節約するために別のプロバイダでテストを回していたことに気づきました。別の開発者は、エージェントが自分のメールアドレスをHTTPヘッダーに入れて送っていたことに気づきました。細部は違っても形は同じです。モデルが一度シークレットを見てしまえば、その後シークレットがどこへ行くかは誰にも制御できません。

手元にあったツールでは防げませんでした。シークレットスキャナはGitを見ます。キーがすでにトランスクリプトに入った後の、コミット時点で捕まえます。denyルールはReadツールを止めますが、bashの`cat .env`は止められません。自分のプログラムがクラッシュ時に吐く設定値も止められません。`CLAUDE.md`の指示はモデルへのお願いであり、強制ではありません。ファイルが必要だと判断したモデルは指示に反論し、ときには勝ちます。

そこで欲しかった制御を自分で作りました。モデルの外側で動く検査です。ツールが実行される前に動き、出力が戻った後にも動き、何かがGitへ入る前にも動きます。それが[Agent Guard](https://github.com/JeongJaeSoon/agent-guard)です。

## 何をするものか

Agent GuardはClaude CodeとCodexのためのローカル優先のガードレールです。ネイティブなGitフックとGitHub Actionも同梱しています。

- ツールが実行される前に、危険な`.env`の読み取りを止めます。エージェントが`git commit`や`git push`を実行すると、ステージされた行をgitleaksで先にスキャンし、シークレットらしい値があればコマンドを止めます。エージェントが検査を切ることはできません。エージェントが実行するGitコマンドでは`--no-verify`と`--no-gpg-sign`を拒否します。
- 出力が戻った後に、対応するツール出力に含まれるシークレットらしい値を、モデルが見る前にマスクします。キーがファイルから来たのか、コマンドから来たのか、プログラムのエラー出力から来たのかは問いません。
- Gitの中では、ネイティブなpre-commitフックが、誰のものであれすべてのローカルコミットをスキャンします。GitHub Actionがプッシュとプルリクエストをもう一度スキャンし、後ろを支えます。

![Agent Guardの動作: 秘密鍵の入った.envの読み取りは止められ、シェル出力ではキーが[REDACTED]と表示されます](https://raw.githubusercontent.com/JeongJaeSoon/agent-guard/main/docs/demo.gif)

## このプロジェクトが目指すもの

設計を決めた原則は3つです。

依存を少なくすること。ランタイムは移植性のあるシェルと`awk`、`git`、`jq`、gitleaksだけです。デーモンはなく、ランタイムフレームワークもなく、監査すべきパッケージの生態系もありません。セキュリティツール自体がサプライチェーンを持ち込めば、解くと言っている問題の一部になります。

邪魔にならない速さ。ガードレールが作業の流れを遅くすれば、切られます。コミットゲートはツリー全体ではなくステージされた追加行だけをスキャンし、検査はエージェントがもともと行っていた流れの中でそのまま動きます。

軽く、ローカルで。ホスト型アカウントはなく、テレメトリもなく、開発者サービスもありません。既定の処理はローカルで一時的に行われます。シークレットを見張るツールがどこかへデータを送っていてはいけません。私に対してもです。

## 難しかったところ

発想は単純です。覆わなければならない表面は単純ではありません。作業の大部分は次のようなケースに行きました。

コミットの書き方は十通り以上あります。`git commit -a`、`--patch`、パス指定、`--include`、`--only`、追跡されていないファイルの対話的ステージング、無視されたファイルへの`git add -f`。どれもコミットに含まれる内容を変えます。ゲートはインデックスにあるものではなく、そのコミットが実際に含む内容をスキャンしなければなりません。Gitが自分でステージする変更も含みます。

エージェントはコマンドの中にコマンドを隠します。シェルコードは`bash -c`、ヒアストリング、`env -S`、`eval`を通って届きます。Gitエイリアスは別のコマンドへ展開されます。`!`エイリアスは任意のシェルを実行します。`help.autoCorrect`は入力されたものと違うサブコマンドを推測することもあります。Agent Guardはそのすべてを、コマンド自体と同じように検査します。`git commit $FLAGS`のように実行時でなければ分からない部分がある場合は、全部をスキャンし、残りはポリシーに決めさせるのが正直な答えです。

スキャンはある一時点の姿です。ゲートはコマンドが始まる時点のファイルをスキャンします。同じコマンドラインの前半が先にファイルを書いてしまえば、スキャンはその結果を見られません。プラグインが唯一の層であってはいけない理由はまさにこれです。ネイティブなpre-commitフックは、Gitが最終内容をステージした後にスキャンします。

スキャンが動かなかったことは、きれいだったことにはなりません。gitleaksがない、あるいは失敗したのにコミットが安全として通れば、ガードレールは最悪の瞬間に開いたまま失敗します。Agent Guardはこの場合を明示し、設定可能にしました。既定では保護が弱まっていることを警告します。`AGENT_GUARD_INFRA_FAILURE_MODE=closed`にすると、代わりに止めます。ネイティブフックとActionは、この設定にかかわらず閉じたまま失敗します。

セットアップは保護を証明しません。プラグインがきれいにインストールされても、ホストがフックを実際に呼ばなければ何も守れません。そこでこのプロジェクトには、実際のセッションで実行する無害なライブ検証プローブが入っています。インストールされたことと動いていることは別の主張だからです。セキュリティツールがこの2つを曖昧にしてはいけません。

## クイックスタート

プラグインをインストールし([インストールガイド](https://github.com/JeongJaeSoon/agent-guard/blob/main/docs/installation.md))、ガイド付きセットアップを実行します。

```text
# Claude Code
/agent-guard:setup-agent-guard

# Codex
$setup-agent-guard
```

エージェントなしで、リポジトリを直接検査することもできます。

```sh
agent-guard scan-working-tree
agent-guard scan-staged
agent-guard scan-path .
```

必要なものはmacOSかLinux、`git`、`jq`、gitleaks 8.30以上だけです。

## 次に力を入れたいもの: PIIフィルタ

漏れるのはシークレットだけではありません。上のメールアドレスの件がその証拠です。エージェントはメールアドレス、電話番号、名前といった個人情報もリクエストやヘッダーやログへ入れます。スキャナがそこを見ていないので、誰も気づきません。

次に力を入れたいのはここです。設定にはすでに初期段階のオプトインPIIサポートがあります。目標はPIIをシークレットと同じように扱うことです。ツールの入出力から個人情報を検出し、モデルが見る前、ログに残る前に消します。難しいのはバランスです。誤検出で普通のコードを壊すフィルタは1日で切られます。カバー範囲と同じくらい精度が要ります。

検討中でもう3つ方向があります。

- ホストの拡張。同じ漏洩はCursor、Gemini CLI、他のエージェントでも起きます。ホストごとにフックの呼び出し方が違うため、サポートとはREADMEにロゴを1つ足すことではなく、ホストごとの検証を意味します。
- Windows。現在は未対応です。このプロジェクトは設計から移植性のあるシェルなので、Windowsには移植ではなく別の答えが必要です。
- 継続的な検証。ホストはバージョンごとにフックの振る舞いを変えます。ベンチマークとライブプローブの作業を続け、守られているという言葉が仮定ではなくテストされた主張であり続けるようにします。

## 正直な限界

Agent Guardは多層防御であり、ボールト(保管庫)でもDLPシステムでもありません。認証情報をローテーションはしません。GitHub Secret Scanning、Push Protection、コードレビュー、まともなキー管理の代わりにもなりません。キー管理とは、ツールごとのキー分離、支出上限、短い寿命のことです。このツールが取り除くのは、私が見続けてきた事故です。誰も気づく前にシークレットがトランスクリプトとログとコミットへ入ることです。

モデルが見たことのないキーは、モデルが漏らすことも、使うことも、コミットすることもできません。
