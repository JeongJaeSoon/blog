이 도구는 문제가 흥미로워 보여서 만든 게 아니다. 눈앞에서 계속 터졌기 때문에 만들었다.

회사에서 실제 개발에 Claude Code를 많이 쓴다. 그리고 한 번이 아니라 여러 번, 세션이 같은 조용한 방식으로 어긋났다. 에이전트가 평범한 작업을 하다가 `.env` 파일을 읽었고, 진짜 API 키가 트랜스크립트 안으로 들어갔다. 키는 LLM에게 전달됐고 세션 로그에 남았다. 복사 한 번이면 가면 안 되는 곳으로 갈 수 있는 상태였다. 경보가 울린 적도, 누군가 무모한 짓을 한 적도 없다. 에이전트는 자기 일을 했을 뿐이다. 그 일은 파일을 읽고 명령을 실행하는 것이다.

r/ClaudeCode의 글들도 같은 이야기다. 어떤 개발자는 에이전트가 `.env`에서 여러 회사의 키를 꺼내 토큰을 아끼려고 다른 프로바이더로 테스트를 돌린 것을 발견했다. 또 다른 개발자는 에이전트가 자기 이메일 주소를 HTTP 헤더에 실어 보내고 있었다는 것을 알았다. 디테일은 달라도 모양은 같다. 모델이 시크릿을 본 뒤에는 그 시크릿이 어디로 가는지 아무도 통제하지 못한다.

기존 도구는 이걸 못 막았다. 시크릿 스캐너는 Git을 본다. 키가 이미 트랜스크립트에 들어간 뒤인 커밋 시점에 잡는다. deny 룰은 Read 도구는 막지만 bash의 `cat .env`는 못 막는다. 내 프로그램이 크래시 나면서 찍어내는 설정값도 못 막는다. `CLAUDE.md`에 적는 지시는 모델에 대한 부탁이지 강제가 아니다. 파일이 필요하다고 판단한 모델은 내 지시와 다투고, 가끔은 이긴다.

그래서 내가 원하던 통제를 직접 만들었다. 모델 바깥에서 도는 검사다. 도구가 실행되기 전에 돌고, 출력이 돌아온 뒤에 돌고, 무언가가 Git에 들어가기 전에 돈다. 그게 [Agent Guard](https://github.com/JeongJaeSoon/agent-guard)다.

## 무엇을 하나

Agent Guard는 Claude Code와 Codex를 위한 로컬 우선 가드레일이다. 네이티브 Git 훅과 GitHub Action도 함께 제공한다.

- 도구가 실행되기 전에 위험한 `.env` 읽기를 차단한다. 에이전트가 `git commit`이나 `git push`를 실행하면 스테이징된 줄을 gitleaks로 먼저 스캔하고, 시크릿으로 보이는 값이 있으면 명령을 막는다. 에이전트가 검사를 끌 수도 없다. 에이전트가 실행하는 Git 명령에서는 `--no-verify`와 `--no-gpg-sign`을 거부한다.
- 출력이 돌아온 뒤에는 지원되는 도구 출력에 포함된 시크릿 형태의 값을 모델이 보기 전에 마스킹한다. 키가 파일에서 왔든 명령에서 왔든 내 프로그램의 에러 출력에서 왔든, 마스킹은 구분하지 않는다.
- Git 안에서는 네이티브 pre-commit 훅이 누가 하든 모든 로컬 커밋을 스캔한다. GitHub Action은 푸시와 PR을 다시 스캔해서 뒤를 받친다.

## 이 프로젝트가 추구하는 것

세 가지 원칙이 설계를 만들었다.

**적은 의존성.** 런타임은 이식성 있는 셸과 `awk`, `git`, `jq`, 그리고 gitleaks뿐이다. 데몬도, 런타임 프레임워크도, 감사해야 할 패키지 생태계도 없다. 보안 도구 자체가 공급망을 끌고 오면 해결하겠다던 문제의 일부가 된다.

**눈에 띄지 않을 만큼 빠른 속도.** 가드레일이 작업 흐름을 느리게 만들면 꺼진다. 커밋 게이트는 트리 전체가 아니라 스테이징된 추가 줄만 스캔한다. 검사는 에이전트가 이미 수행하던 흐름 안에서 인라인으로 돈다.

**가볍고 로컬하게.** 호스팅 계정 없음, 텔레메트리 없음, 개발자 서비스 없음. 기본 처리는 로컬에서 일시적으로 이뤄진다. 내 시크릿을 감시하는 도구가 어딘가로 데이터를 보내면 안 된다. 나에게조차도.

## 어려웠던 부분

아이디어는 단순하다. 그런데 커버해야 할 표면이 단순하지 않다. 작업의 대부분은 이런 케이스에 들어갔다.

**커밋을 적는 방법은 열두 가지도 넘는다.** `git commit -a`, `--patch`, 경로 지정, `--include`, `--only`, 추적 안 되는 파일의 인터랙티브 스테이징, 무시된 파일에 대한 `git add -f`. 각각이 커밋에 들어가는 내용을 바꾼다. 게이트는 인덱스에 뭐가 있는지가 아니라 그 커밋이 실제로 포함할 내용을 스캔해야 한다. Git이 스스로 스테이징하는 변경까지 포함해서다.

**에이전트는 명령 안에 명령을 숨긴다.** 셸 코드는 `bash -c`, here-string, `env -S`, `eval`로 도착한다. Git alias는 다른 명령으로 풀린다. `!` alias는 임의의 셸을 실행한다. `help.autoCorrect`는 입력한 것과 다른 서브커맨드를 추측하기도 한다. Agent Guard는 이 전부를 명령 자체처럼 검사한다. `git commit $FLAGS`처럼 실행 시점에야 알 수 있는 부분이 있으면, 정직한 답은 전부를 스캔하고 나머지는 정책이 정하게 두는 것이다.

**스캔은 어느 한 시점의 사진이다.** 게이트는 명령이 시작되는 시점의 파일을 스캔한다. 같은 명령줄의 앞부분이 파일을 먼저 써버리면 스캔은 그 결과를 볼 수 없다. 플러그인이 유일한 층이 아니어야 하는 이유가 정확히 이것이다. 네이티브 pre-commit 훅은 Git이 최종 내용을 스테이징한 뒤에 스캔한다.

**스캔이 돌지 않았다는 것은 깨끗하다는 뜻이 아니다.** gitleaks가 없거나 실패했는데 커밋이 안전하다고 통과하면, 가드레일은 최악의 순간에 열린 채로 실패한다. Agent Guard는 이 경우를 명시적이고 설정 가능하게 만들었다. 기본은 보호가 약해졌다고 경고하는 것이다. `AGENT_GUARD_INFRA_FAILURE_MODE=closed`로 두면 대신 차단한다. 네이티브 훅과 Action은 이 설정과 무관하게 닫힌 채로 실패한다.

**설치는 보호를 증명하지 못한다.** 플러그인이 완벽하게 설치돼도 호스트가 훅을 실제로 호출하지 않으면 보호는 없다. 그래서 이 프로젝트는 실제 세션에서 돌리는 무해한 라이브 검증 프로브를 제공한다. 설치됐다는 말과 작동한다는 말은 다른 주장이기 때문이다. 보안 도구가 이 둘을 흐리면 안 된다.

## 빠른 시작

플러그인을 설치하고([설치 가이드](https://github.com/JeongJaeSoon/agent-guard/blob/main/docs/installation.md)) 가이드 셋업을 실행한다.

```text
# Claude Code
/agent-guard:setup-agent-guard

# Codex
$setup-agent-guard
```

에이전트 없이 저장소를 직접 검사할 수도 있다.

```sh
agent-guard scan-working-tree
agent-guard scan-staged
agent-guard scan-path .
```

필요한 것은 macOS나 Linux, `git`, `jq`, gitleaks 8.30 이상이 전부다.

## 앞으로 힘을 싣고 싶은 것: PII 필터

새는 것은 시크릿만이 아니다. 위의 이메일 사례가 증거다. 에이전트는 이메일 주소, 전화번호, 이름 같은 개인정보도 요청과 헤더와 로그에 넣는다. 스캐너가 그걸 보고 있지 않으니 아무도 모른다.

다음으로 힘을 싣고 싶은 곳이 여기다. 설정에는 이미 초기 단계의 옵트인 PII 지원이 있다. 목표는 PII를 시크릿과 같은 방식으로 다루는 것이다. 도구 입출력에서 개인정보를 탐지하고, 모델이 보거나 로그가 남기기 전에 지운다. 어려운 것은 균형이다. 오탐으로 멀쩡한 코드를 망가뜨리는 필터는 하루 만에 꺼진다. 커버리지만큼 정밀도가 중요하다.

열어두고 검토 중인 방향이 세 가지 더 있다.

- **호스트 확장.** 같은 유출은 Cursor, Gemini CLI, 다른 에이전트에서도 일어난다. 호스트마다 훅을 호출하는 방식이 달라서, 지원은 README에 로고를 하나 더 붙이는 일이 아니라 호스트별 검증을 뜻한다.
- **Windows.** 현재는 미지원이다. 이 프로젝트는 설계부터 이식성 있는 셸이라, Windows에는 이식이 아니라 다른 답이 필요하다.
- **지속적인 검증.** 호스트는 버전마다 훅 동작을 바꾼다. 벤치마크와 라이브 프로브 작업을 계속해서, 보호된다는 말이 가정이 아니라 테스트된 주장으로 남게 한다.

## 솔직한 한계

Agent Guard는 심층 방어이지 볼트(금고)가 아니고 DLP 시스템도 아니다. 자격증명을 교체해 주지 않는다. GitHub Secret Scanning, Push Protection, 코드 리뷰, 멀쩡한 키 관리를 대체하지도 않는다. 키 관리는 도구별 키 분리, 지출 상한, 짧은 수명을 말한다. 이 도구가 없애는 것은 내가 계속 목격하던 그 사고다. 아무도 알아채기 전에 시크릿이 트랜스크립트와 로그와 커밋에 들어가는 일.

모델이 본 적 없는 키는 모델이 흘릴 수도, 쓸 수도, 커밋할 수도 없다.

MIT 라이선스 오픈소스다: [github.com/JeongJaeSoon/agent-guard](https://github.com/JeongJaeSoon/agent-guard). 네 트랜스크립트에서 시크릿 하나라도 지켜줬다면, 스타가 다른 개발자들이 이걸 찾는 데 도움이 된다.
